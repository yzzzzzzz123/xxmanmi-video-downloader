# 内容质量与结构化输入

## 写作判断

- 找一个具体读者问题：是否值得补、观看顺序、近期消息有什么变化、为何某个片段/配乐值得注意。根据题目组织结构，不强行每篇“三个看点”。
- 自然、具体，不堆“神作”“炸裂”“必看”“全网第一”；不用虚构的观看经历、评分或观众共识。不冒充童锦程等真实人物。
- 事实和编辑解读分开。避开重要结局剧透，确需剧透时明确提示。不把某地区的上线公告写成全球可看；不未经核验宣传漫映已有完整资源。
- 配图围绕相邻内容，图片有出处与必要权属说明。检查人物、文字是否被封面裁掉；不能用无关热图凑数。
- 默认选近期新番、新电影或新一季，核验播出时间和进度；连续新稿不由古早经典主导。配图优先动漫本身的官方剧照、场景图、宣传海报，画面须清晰、美观、与段落相符；用户未明确要求时，不自制图卡、流程图或AI仿作。
- AI参与写作或配图时使用平台实际提供的合适创作标注。用户已要求后续每篇声明原创：以有独立表达的自写正文为目标，核对符合当前平台条件后声明「文字原创」，作者为漫映Manying。第三方剧照注明出处及权属，不声明为自有画面；转载、拼凑或不符合条件的内容不能作虚假声明。原创与AI来源是不同设置，均按实际情况保留；赞赏不随原创自动开启。

## 文章轮换

用户要求每次文章的类型与风格都要轮换。起稿前先用CLI查看近期真实稿件，再按需读取其`research.md`或正文，比较选题、类型、口吻、图文组织和互动方式。不要加载整个历史，也不把仅换作品名或封面当作轮换。同一次要求发布多篇时，各篇也须彼此有不同的类型与风格。

可结合题材选择画面故事、细节拆解、误解澄清、观看指南、作品对照、消息速读或读者互动等类型；这只是可选方向，不是固定顺序或必须使用的栏目。叙事可从一个场景、一个问题、一个细节或一条消息切入，图文可按故事推进、线索揭晓、逐图解读或实用步骤组织。标题句式、开头和结尾也要随类型变化，避免每篇都是清单、问句或字母投票。

保留真实相关配图、短段落与清楚来源。轮换关注内容表达与阅读节奏，不靠增加装饰或拉长正文制造差异。把本篇选定的类型、口吻、图文组织、互动方式及与近期稿件的差异简记在`research.md`；没有互动需要时可自然收尾，不硬凑提问。以最终正文是否真正不同作为判断，不以改了风格标签代替检查。用户当次明确指定的题材、格式和口吻优先。

深度与节奏也参与轮换。有的篇目深入一个细节或问题，有的篇目用画面与短句快速读完；不要把内容丰富理解成所有文章加长、加重。将结构化的`editorial`信息写入`content.json`，字段为`type`、`tone`、`layout`、`interaction`、`depth`、`pace`、`angle`，便于每日存档和下篇选题比较。

## 动态素材与网站入口

- 按内容需要，在相应段落加入自有或授权视频、动图；不为凑形式放无关素材。自制示意动画标明性质，不能冒充影片片段。注册GIF沿用图片流程；核验本地多帧、微信实际保留GIF格式与动画、正文位置和移动端观感。视频走微信原生上传入口，并检查转码、播放、封面和字幕；本地CLI不把视频伪装成图片。
- 每篇`content.json`写入`website_url: "https://manying.site/"`，正文末尾自然介绍网站，例如「我们的网站是 https://manying.site/，想看的电影、动漫可以来这里找找。点文末‘阅读原文’就能打开。」根据文章语境调整措辞，不沿用「这里有你想看的」式广告标题，不未经核验承诺某片已收录。
- 后台勾选「原文链接」并实际填写该网址。保存和公开页都检查「阅读原文」入口；正文网址不替代原生入口。

## 每日存档与查重

使用`scripts/archive_articles.py`，本地操作，不接入微信凭据：

```powershell
$archiveCli = './skills/manying-wechat-publisher/scripts/archive_articles.py'
python -X utf8 $archiveCli archive --root $articleRoot --date 'YYYY-MM-DD'
python -X utf8 $archiveCli check --root $articleRoot --dir $articleDir
```

起稿前更新每日索引并查看近期条目；发表前检查相同标题、正文和主体段落，以及相似内容、角度和重复配图。精确重复须改稿；相似度和配图重用是复核线索，必须读具体差异，不能由分数替代编辑判断。网站介绍、图注和来源不计入主体正文相似度。每天按北京时间存档已发表条目的全文、公开链接、图片哈希和类型/深度/节奏，不覆盖或改写已经发表的原稿。仅在后台存在的旧稿单独登记公开标题、链接与时间，标明全文尚未本地归档。

正式发表并核实后再次更新当天索引。记录文件在文章根目录的`archive/YYYY-MM-DD.json`，原稿和素材继续留在对应文章目录，存档不保存临时预览URL、登录参数或二维码。

## content.json合同

`new`会创建空白工作稿。用apply_patch编辑`content.json`，而非把整篇文章作为巨大的命令行参数。示例只是格式，不是已经核验的文章：

```json
{
  "summary": "简短说明文章对读者有什么用。",
  "sources": [
    {
      "title": "实际来源标题",
      "url": "https://官方域名/实际页面",
      "checked_at": "核验日期",
      "claims": ["这个来源支持的具体事实"]
    }
  ],
  "blocks": [
    {"type": "p", "text": "具体的开头，不写空泛铺垫。"},
    {"type": "image", "file": "cover.jpg", "caption": "图片说明与真实出处"},
    {"type": "h2", "text": "与内容相关的小标题"},
    {"type": "p", "text": "正文，事实与观点分开。"}
  ],
  "disclosure": "消息来自所列来源，观看角度为编辑解读；配图的真实性质。"
}
```

- `type`仅支持`p`、`h2`、`image`、`hr`。文字由CLI转义，不接收任意脚本或文章HTML。
- 图片`file`必须是当前文章目录内的真实文件，并经`fetch-image`或`register-image`注册；源图片不在程序里重复发给模型，人工/模型只看实际需核验的图。
- `article.html`使用本地相对图片，供离线视觉检查；`paste.html`没有微信原生图片映射时显示醒目的图片占位，不能直接发布。
- 上传微信后，将当前正文图片的实际`outerHTML`保存为`native-images.json`：`{"cover.jpg":"<img ...>","another.jpg":"<img ...>"}`。这里仅保存图片DOM，不保存编辑器URL、token或任何账号凭据。
- CLI校验这些原生标签确为微信CDN图片后，`render`把它们放回预定图片位置，避免通过移动光标插图把正文切断。
- 来源在文末各自成段，保留可读的来源名称和公开URL；微信可能移除外链功能，不依赖链接仍可点击。

## 排版

默认正文16px/行高30px，二级标题19px/行高30px，图注11px/行高20px，资料12px/行高24px。明确px单位，来源段不把多种字号和低行高嵌在同一段。合适的留白比装饰更重要。

CLI校验只保证结构和文件一致性。文章是否准确、好读、配图相关、微信最终渲染正常，必须根据真实证据核验；不能把CLI退出0写成全文事实已经自动通过。
