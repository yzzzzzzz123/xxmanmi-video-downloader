# 漫映项目发布操作细则

本流程发布节目之外的项目变更。节目、播放资源和对应封面由 [节目同步 Skill](../../manying-production-sync/SKILL.md) 执行；联合调用时按末节协调。

## 范围与发布前核对

1. 读项目 AGENTS.md、当前源码和 git status，比较生产现状，冻结本次发布文件、依赖、配置、结构迁移及非节目内容/配置数据清单。只读核对未提交和未跟踪文件，不能将它们一律遗漏，也不能将整个工作目录镜像到生产。
2. 根据 web/ 当前 Python 导入图、静态引用和运行路径构建完整应用，包含新增模块与网页资产。修改 UI、增加栏目、改网页内容均在本 skill 范围；栏目若存于代码、JSON 或数据库，按实际来源分别打包或设计受控内容迁移。
3. 与变更相称地验证本地应用、页面和关键业务流程。经严格主机密钥校验的 SSH 检查服务状态、磁盘空间、当前应用/依赖版本、数据库结构与可用备份。核对 sudo -n 和实际运行账号；缺少执行条件时说明具体阻碍，不在生产试错。
4. 记录节目与资源数量、最大 ID，以及账号、会员、会话、订单和用户行为等生产表的安全聚合指标。不得导出或打印密码哈希、个人信息或会话令牌。迁移后要验证实际网站数据库账号的读写权限；简单健康查询不能替代业务验收。

## 备份、打包与暂存

1. 写入前在仅受限账号可读的生产备份目录做完整 pg_dump -Fc，运行 pg_restore -l 验证可读；另备份当前 app、依赖版本/venv 指向、受影响 systemd/Nginx/应用配置及拟变更的非节目内容。备份不置于 Web 可访问目录，不拷入仓库。
2. 打包本次完整可运行应用与依赖清单，并逐文件核对 SHA-256。排除 .git、本机秘密、.env、venv、缓存、日志、DBeaver 文件、下载资料和本地数据库文件；运行所需资产与开发材料分别识别，不能使用旧文件白名单遗漏新模块。
3. 在生产独立版本目录暂存，按新版本需要构建独立 venv 或可回退依赖环境，保留当前运行版本。验证导入、配置合并、运行用户权限与静态资产；不直接覆盖正在运行的 app 使回退点丢失。
   版本目录在受限 `umask` 下创建后，显式设置每一级父目录的属组与可遍历权限；不能把 `mkdir(mode=0750)` 当成最终权限已是 0750。备份仍保持仅管理员可读。以真实服务账号从暂存目录验证 Python 导入、数据库权限及业务查询，失败时先检查整条目录路径的权限，再决定是否缺模块；切换前必须通过，复用已完成备份继续校验。
4. web/deploy/build-bundle.ps1、install.sh、finish-install.sh 属于初装资料；复用前检查实际能力，不在已安装生产环境重跑初始化。历史 .runtime/release/ 脚本中的固定计数、路径和包清单不得作为本轮事实。

## 结构、配置和网站内容变更

1. 将当前结构定义与生产实际列、约束、索引、视图、函数及权限对比；CREATE TABLE IF NOT EXISTS 不能代替迁移。必要变更使用有版本记录或可重复的前向 SQL，先在隔离本地环境或备份副本演练。账户/会员等表结构可迁移，但已有生产行及权限必须保留。
2. 网站栏目、页面文案等存于数据库时，逐表划定受控字段与稳定键，事务内核对预期变化，保护生产专属记录。不能以其他所有修改为由导入本地账号、会话、支付订单或用户状态；不能把 programs/resources 内容修改藏入网站配置迁移。
3. 应用配置、服务配置和反向代理变更以生产现有文件为底进行受控合并，保留真实环境地址、密钥和路径。项目没有相关变更时不重建生产网络入口、不新开数据库公网端口。
4. 结构变更优先保持旧版/新版兼容，再切换代码。删除列或其他不可逆变更根据本次实际需求制定恢复与维护安排，不能依赖事后整库恢复抹掉线上新用户操作。

## 切换、验收与失败恢复

1. 保留上一版目录与依赖环境，以可回退方式切换 app/版本指针；仅重启本次实际需要的网页服务。核对 manying.service、日志和 http://127.0.0.1:8088/api/health；应用与 PostgreSQL 保留既有回环监听和安全入口配置。
2. 从现有生产入口检查本次变更：UI 排版与交互、栏目、网页内容、静态资产、首页、列表、详情、账号流程和播放接口；有新行为统计或新表时验证真实业务查询及受控写入。不得创建或冒用真实用户账号代替测试；使用已获授权的测试身份或说明尚待用户验收的部分。
3. 核对生产权威数据未被迁移或发布覆盖，将并发用户操作造成的正常变化与本次写入区分；检查采集数据库、线程、终端和浏览器没有被网页发布顺带重启。
4. 健康或关键业务失败时切回上一版兼容代码、依赖及本次变更的配置并恢复网页服务。对已提交结构/内容迁移，根据记录和备份修复，不能在新用户活动后盲目恢复整库。报告已部署版本、验证结果和剩余问题。

## 两项 Skill 的完整联合发布

1. 用户同时要求两项 Skill，或明确要求全部本地项目修改上线时，完整读取两项 Skill 及对应细则。冻结共同快照/总清单：项目文件、依赖、结构与网站配置/内容归本流程，节目、资源与节目封面归节目同步；共用本次可恢复备份，分别保存结果。
2. 根据版本兼容性安排步骤：暂存并验证新应用 → 必要且兼容的前向迁移/网站配置或内容变更 → 由节目同步 Skill 合并冻结清单内节目、资源和封面 → 切换兼容应用 → 验收两部分。需要不同顺序时在清单中说明依赖与恢复点；不机械地串联两个忽略彼此的脚本。
3. 用户明确要求一次性完整同步时，节目清单覆盖全部本地节目管理差异，包括空、raw、失败和历史记录，不按认可状态筛选。当前常规采集使用事件增量，不等待 300 个节目；技术核对或身份冲突未通过时保留未完成，不能假报可播放或宣称全部一致。
4. 两部分都成功才报告完整同步；任一部分失败或仅部分部署时，分别说明实际状态并继续处理可恢复问题。完整同步指可发布的本地项目成果，不要求生产用户数据、凭据和运行状态与本地镜像一致。
